# 技术选型方案(2026-08-06 更新:确认采用方案B)

> 本文档为实际采用的技术路线记录。曾推荐"方案A纯MaxKB",实际开发中因需要稳定实现组卷/判卷/错题等结构化业务,演进为**方案B(MaxKB + 自研FastAPI + Vue3)**,不再回退。

## 一、推荐方案对比

### 方案A：纯MaxKB搭建
| 层 | 技术 | 说明 |
|---|---|---|
| 智能体平台 | 飞致云MaxKB | RAG知识库、工作流编排、多模型接入 |
| 前端 | MaxKB内置应用界面 + 嵌入页面 | 或自写简单HTML/JS嵌入 |
| 后端 | MaxKB API + Python脚本 | Python处理PPT生成、Excel导出等 |
| 知识库 | MaxKB内置(PgVector) | 上传文档自动分段+向量化 |
| 模型 | DeepSeek (API) | 已接入 |
| 部署 | Docker | 本地 8081 端口 |

**优点**：开发快、低代码。**缺点**：组卷/判卷等结构化业务在MaxKB工作流中实现复杂、调试成本高；界面灵活性有限。

### 方案B：MaxKB + 自研前端/后端 ✅ 实际采用
| 层 | 技术 | 说明 |
|---|---|---|
| 智能体平台 | MaxKB(v2.10.4, Docker) | 知识库、RAG对话、智能体工作流(平台助手/学情) |
| 前端 | Vue3(门户, vite) | 学生端/教师端双端界面 |
| 后端 | Python FastAPI | 题库/组卷/判卷/错题本/学情统计/知识库代理 |
| 知识库 | MaxKB内置(PgVector) | 高数/英语/平台三库,blend混合检索 |
| 模型 | DeepSeek(LLM) + maxkb-embedding(本地向量) | 已接入 |
| 存储 | SQLite(aiplatform.db) | 题库/试卷/错题等结构化数据 |

**优点**：界面灵活、结构化业务稳定、功能完整、差异化亮点(学情看板等)。
**缺点**：需要前后端能力(已具备)。**采用理由**：P0闭环(组卷→作答→判卷→错题)已用FastAPI跑通,MaxKB专注RAG对话与智能体,各司其职。

### 方案C：纯代码开发
| 层 | 技术 | 说明 |
|---|---|---|
| AI框架 | LangChain / LlamaIndex | 自建RAG流程 |
| 前端 | Vue3 / React | 完全自研 |
| 后端 | Python FastAPI | 全栈自研 |
| 向量库 | ChromaDB / Milvus | 自建知识库 |
| 模型 | DeepSeek API | 调用大模型 |

**优点**：完全可控。**缺点**：工作量大、重复造轮子,已弃用。

## 二、实际技术路线(方案B,已落地)

```
门户 Vue3 (:5173) ── vite proxy ──┬── /chat, /admin → MaxKB (:8080)   [AI对话/知识库/智能体]
                                  └── /api          → FastAPI (:8001)  [题库/组卷/判卷/错题/学情/知识库代理]

MaxKB (Docker, :8081)：
  模型: DeepSeek (LLM) + maxkb-embedding (本地向量)
  知识库: AI教辅智学平台(307段) / 高等数学(149段,已清理标题段) / 大学英语(15段)
  应用: AI微积分助教 / AI英语助教 / AI教辅智学平台助手(SIMPLE)
  工作流: 平台助手/学情分析(建设中)

FastAPI (:8001, SQLite)：
  questions.py  题库(手动录入 + DeepSeek批量生成,高数81题/英语15题)
  papers.py     智能组卷/在线作答/自动判卷/错题本
  knowledge.py  知识库代理(浏览/检索,内部持admin token)
  database.py   SQLite(aiplatform.db)
```

**职责边界**：
- **MaxKB管**：知识库、RAG对话、智能体工作流(平台助手、学情分析)
- **FastAPI管**：结构化数据与业务逻辑(题库、组卷、判卷、错题、学情统计)、知识库代理
- **门户管**：学生端+教师端界面(同一套Vue3)
